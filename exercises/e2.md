### 1. Reading a Concept
1. The first invariant is that for a given request, the number of purchases cannot exceed the count requested. The second is that each purchase corresponding to a request must be associated with the same item. The first is more important, because it ensures that the owner of the registry cannot receive more of any given item than they requested. The design of the purchase action is most affected by this invariant. The purchase action has a precondition preventing a user from making a purchase that would make the total purchase count exceed the total request count.
2. The removeItem action fails to preserve the first intended invariant. The following sequences of actions could occur:
```
create(owner: sarah)
addItem(registry: sarahRegistry, item: blender, count: 1)
open(registry: sarahRegistry)
purchase(purchaser: leo, registry: sarahRegistry, item: blender, count: 1)
removeItem(registry: sarahRegistry, item: blender)
```

which would result in 1 purchased blender and 0 requested blenders. We could fix this problem by only allowing the owner to remove an item when it has no associated purchases.
3. Yes, you can open or close a registry as long as it exists, so since registries are not deleted, they can be opened and closed repeatedly. We may allow this because the owner may close the registry, invite a new guest to their event last minute, and want to be able to reopen the registry for their new guest.
4. We may want to be able to delete a registry such that we don't have a huge history of registries from prior events taking up space on our hardware. However, we may also want to avoid deleting registries, and instead rely upon the "active" flag, so that users can see their prior registries and share them with other users, or use them as inspiration for their next event.
5. Two common queries will be: (1) `addItem(registry, item, count)` for owners adding items to registries and (2) `purchase(purchaser, registry, item, count)` for gift givers buying gifts.
6. You could add an `anonymous Flag` argument to the Registry state, which specifies whether the purchasers should be kept hidden from the owner for that registry.
7. This is preferable because it makes the representation of items flexible and keeps the concept definition abstract. We are able to abstract away exactly how we represent items in our software and focus on the higher-level courses of action that can occur.

### 3. Comparing concepts
**concept** PersonalAccessTokening
**purpose** limit the consequences of leaked credentials by making credentials limited and revocable
**principle** a user creates personal access tokens with selected scopes;
the scopes limit what each token can be used for;
the user can change a token's scopes or revoke it.
**state**
a set of Tokens with
	an owner User
	a name String
	an active Flag
	a set of Scopes
**actions**
create (owner: User, name: String, scopes: set of Scopes) : return (token: Token)
	**then** create a new token with the given scopes and name, set active to true, and return it.

authenticate (token: Token) : return (user: User, scopes: set of Scopes)
	**where** token exists and is active
	**then** return the owner and scopes of the token
	
changeScopes (token: Token, scopes: set of Scopes) : return ()
	**where** token exists and is active
	**then** set the token's scopes to the inputted scopes

delete (token: Token) : return ()
	**where** token exists and is active
	**then** set active to false

This concept differs from *PasswordAuthenticating* because it can grant limited, temporary access to a User's resources, in contrast to the complete, permanent access of a password. This allows users to maintain multiple credentials with different capabilities. If one of their tokens gets leaked, the User can easily revoke the token. To better explain this, I might change the documentation to not say that a token acts as your password, but rather say that it allows you to create many authentication methods, each of which may grant you different capabilities.

### 4. Defining familiar Concepts

**concept** URLShortening
**purpose** make a URL easier to share
**principle** users *create* a shortened URL for their link with their preferred alias;
the shortened URL always *redirects* to their link
**state**
a set of ShortURLs with
	a longURL URL
	an alias String
	an expires Date
**actions**
create (longURL: URL, alias?: String, expires: Date) : return ( shortURL : ShortURL)
	**where** alias, if provided, does not exist for a non-expired ShortURL
	**then** create a shortURL with the provided alias, if an alias is provided, or by using a unique generated string as an alias. Set the expires date.
	return shortURL

redirect(shortURL: URL) : return (longURL: longURL)
	**when** shortURL exists and its expiration date has not passed
	**then** return the longURL of shortURL


**concept** ShoppingCart
**purpose** to keep track of the items a user may want to purchase
**principle** a User creates an empty shopping cart;
As they shop, they may add and remove items in the cart to indicate what they intend to purchase;
Finally, when the user is done shopping, they checkout with the current set of items in the cart.
**state**
a set of ShoppingCarts with
	a unique shopper User
	an entries set of Entries

a set of Entries with
	an item Item
	a count Number
**actions**
create (shopper: User) : return (shoppingCart: ShoppingCart)
	**where** shopper does not already have a cart
	**then** create a new shoppingCart with this shopper, containing no entries
	return shoppingCart

addItem (shoppingCart: shoppingCart, item: Item, count: Number) : return ()
	**where** shoppingCart exists and count is greater than zero
	**then** if item is already in shoppingCart, add the new count to the current count. 
	If not, add item to shopping cart with associated count.

removeItem (shoppingCart: shoppingCart, item: Item, count: Number) : return ()
	**where** shoppingCart exists, the inputted count is greater than zero, and the shoppingCart has a count for this item no less than the inputted count
	**then** if the inputted count equals the count of the entry, remove the entry
	otherwise, decrement the count for the inputted item in the shoppingCart by the inputted count
	
checkout (shoppingCart: shoppingCart) : return (items: a set of Items)
	**where** the total count of items in the shopping cart is greater than zero
	**then** remove all items from the shoppingCart and return the set of Items.


**Note:** By making the shopper unique, we ensure that each shopper can only have one shopping cart at a given moment. Additionally, we consider an item to be generic. It may have certain other qualities like color and size, which we do not specify.

**concept** TOTP
**purpose** provide a second authentication factor without requiring the server to send an authentication code to the user's device during each authentication.
**principle** when a user registers, a secret is generated by the server and shared with the user's device;
when the user authenticates, the client generates a time based one-time password using its secret and the current time;
the user provides this password to the server, which independently generates a password from its secret and the current time;
if the passwords match, the user can login.
**state**
a set of ServerRegistrations with
	a unique User
	a unique serverSecret Secret

a set of ClientRegistrations with
	a unique User
	a unique clientSecret Secret
**actions**
register (user: User) : return (serverRegistration: ServerRegistration, clientRegistration: ClientRegistration)
	**where** the user has no server or client registration
	**then** generate a secret;
	create a ServerRegistration on the server and a clientRegistration on the client, each with the secret and the inputted User;
	return serverRegistration, clientRegistration

generate (user: User, time: Time) : return (password: Password)
	**where** the inputted user has a client registration
	**then** return $C(clientSecret, time)$

authenticate (user: User, password: Password, time: Time) : return (user: User)
	**where** the user is registered on the server and the given password equals $C(serverSecret, time)$ for the user's server registration.
	**then** return the user.

**Note:** serverSecret is stored by the server and clientSecret is stored on the user's device. $C$ is some cryptographic function.
