Exercise 3: Composing Concepts

### Concepts for URL Shortening
1. The contexts describe the set of strings among which a new generated string must be unique. A generated string only has to be unique within its given context. In the URL shortening app, a context will be the shortUrlBase, containing a set of shortURL Strings.
2. (a) NonceGenerating must store sets of used strings in order to determine that, when it generates a new string, it is unique. (b) In that implementation, the set of used strings are all the values up to, and including, the current value of the counter for that context.
3. (a) One advantage of this scheme, especially in comparison to the counter implementation, is that common dictionary words are very easy to remember. One disadvantage is that it may be easier for bad actors to guess and access the shortened URL, because the suffixes are common. (b) To realize this idea, I would modify the NonceGenerating concept to also store a set of commonDictionaryWords in its state. The generate action would then randomly choose a word from that set.

### Reactions for URL Shortening
1. In the generate reaction, we don't need the targetUrl argument, because we are only generating a nonce from the shortUrlBase context. All we need to know is the context. To register a shortenedUrl, however, we need to know the targetUrl.
2. This convention isn't used in every case because some variables are used across multiple concepts. For example, instead of calling the shortUrlSuffix variable by its argument name (also shortUrlSuffix), we call it nonce, because the suffix was actually a nonce generated by the NonceGenerating concept.
3. The *request* action is included in the first two actions because they involve the user making a request to the system. Specifically, the user is making a request to shorten a Url. The setExpiry reaction does not include a *request* action because it occurs in response to an action from a concept, specifically a shortenedUrl being registered, rather than an action from a user.

### Extending the Design
1. I would add the following two concepts:

```
concept Counting[Context]
purpose track a count for some context
principle each increment and decrement changes the count for a given context by one
state
	a set of Contexts with
		a count Number
actions
	initialize (context: Context) : (count: Number)
		where a count does not exist for this context
		then initialize count for this context to 0
	increment (context: Context) : (count: Number)
		where a count has been initialized for this Context
		then increase the count for this context by one and return that count
	decrement (context: Context) : (count: Number)
		where a count has been initialized for this Context
		then decrease the count for this context by one and return that count
	_getCount (context: Context) : (count: Number)
		where a count has been initalized for this context
		return the count
		
		
concept Ownership[Resource, User]
  purpose record who owns a resource; restrict access to its owner
  principle after assigning an owner to a resource, ownership lookup returns that user
  state
    a set of Resources with
      an owner User
  actions
    assignOwner (resource: Resource, user: User)
      where resource does not already have an owner
      then associate user as the owner of resource

    getOwner (resource: Resource): (user: User)
      where resource has an owner
      then return the owner
```
